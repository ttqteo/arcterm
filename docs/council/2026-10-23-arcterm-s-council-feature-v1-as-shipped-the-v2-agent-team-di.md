# Council: arcterm's Council feature (v1 as shipped, the v2 agent-team direction and its Phase 0/0b benchmark)

You asked: council việc feature council đi — review the Council feature itself: what is wrong with it, what to change, and where it should go next.

**The Council's main fault is that it costs 3 to 10 times what it quotes (estimate at pkg/council/estimate.go:53 against 4.4M–17.5M measured at docs/council-phase0.md:347) with nothing bounding a call once it starts, so it should stop starting unasked, bound each expert call, default to one agent with the panel opt-in, and get a benchmark that can separate variants before the v2 room or any further benchmark spend.**

The panel agrees on the diagnosis. The price on Start council and in the skill is several times too low, a running council is bounded only by a 10-minute timeout per call, and the benchmark cannot yet tell one agent from a panel. Every expert therefore wants the agent-initiated start turned back into an ask, and the v2 agent-team room deferred. The two most-picked directions are bounding each expert call (3 picks) and making one agent the default with the panel opt-in (4 picks across its merged proposals). Both sit at 9 and 10 only because the ranking rule puts unchallenged directions first. In both cases the challenges target the supporting arguments, not the change itself. That is the weakness the agreed proposal on ranking directions in Go points out. Read the picks, not only the rank. The panel was missing four roles. It had no backend reliability or concurrency reviewer, though most of the defects found are in Go. It had no evaluation methodologist, so the Skeptic carried the benchmark critique alone. No one spoke for the agent that calls the skill unprompted (the broken `wait` read-back shows that gap). No one represented the paper-review user, whose group has no benchmark case and a brief hard-coded to CCS and NDSS. The person gave no replies in this council.

- **Skeptic** proposes · P4 · Rank directions in Go from stored picks, not by an LLM rule that puts "nobody challenged it" first and double-counts merges
  The Review synthesis prompt says to put directions no expert challenges or opposes first, and only then rank by picks, summed over every proposal a direction merges. Both parts break. Challenges are made without code access, and an accept costs nothing (an accept with no words is kept), so "unchallenged" mostly measures how bland or uncheckable a proposal is. A proposal with three picks and one challenge ranks below an unchallenged proposal with none. Summing picks over merged proposals counts one expert twice if they picked two members of the same merged direction, so merging inflates a rank. The v2 spec defines the vote as how many agents put an idea in their top 3, which the Review prompt does not follow. `Council.Picks` is already stored per expert, `writePicks` already counts per proposal, and `cleanSummary` never re-sorts, so the order is whatever the model decides. Change: the model merges and words only. Go computes unique pickers per merged direction, sorts by that, and shows "challenged by X" as a flag instead of a ranking key. This is deterministic and testable without a model call.
